## 2. Small Vivado tests

For each test: close any previous simulation, open **Simulation Settings**,
choose the named **Simulation set**, confirm its top, click **OK**, then
**Run Simulation > Run Behavioral Simulation > Run All**. Read the automatic
PASS line in the Tcl Console pane; no command needs to be typed there.

If this is your first Vivado run, start with **`sim_1` / `tb_alu`**.
Expected: `PASS tb_alu: 4142 checks`. Add `operand_a`, `operand_b`, `alu_op`,
`result`, and `zero` to the wave window. The first ADD wraps `ffffffff +
00000001` to `00000000`, with `zero=1`.

Then follow these small steps:

1. **AES maths:** `sim_aes_primitives` / `tb_aes_primitives`.
   Expected: `PASS tb_aes_primitives: 1810 checks`.
2. **AES alone:** `sim_aes_core` / `tb_aes128_core`.
   Expected: `PASS tb_aes128_core: 17433 checks, 556 completed blocks`.
   Inspect 25-135 ns: START is accepted, BUSY rises, and DONE follows with
   ciphertext `69c4e0d86a7b0430d8cdb78070b4c55a`.
3. **CPU-facing AES registers:** `sim_aes_mmio` / `tb_aes_mmio`.
   Expected final prefix: `PASS tb_aes_mmio`. The two wait configurations
   pass **26,632** and **48,264** checks. Inspect `valid`, `ready`, `addr`,
   `write`, `wdata`, `rdata`, `busy`, and `done` under `normal_bus/dut`.
   A write takes effect only at a rising clock edge with VALID and READY.
4. **Real CPU runs encryption:** `sim_soc_aes` / `tb_soc_aes`.
   Expected final prefix: `PASS tb_soc_aes`. It checks **32 healthy blocks**
   across normal/delayed buses and reset/restart runs, plus deliberate
   mismatch, timeout, and missing-peripheral faults.
   Under `normal_bus/dut`, view the `mmio_*`, `aes_busy`, `aes_done`, and
   `trace_*` signals. Look for a write of 1 to `40000000`, status reads at
   `40000004`, then ciphertext reads at `40000030` through `4000003c`.
5. **Board wrapper:** `sim_aes_board` / `tb_aes_board`.
   Expected final prefix: `PASS tb_aes_board`, including **13 monitor
   scenarios**. Observe the healthy LED pattern before injected faults.

These benches deliberately exercise failures. A temporary fault signal
is expected in those cases; the final PASS line decides the test result.
A `$finish` after PASS is normal. Run All is needed because the project
opens the simulation at 0 ns.

Save a screenshot of each PASS line and at least one waveform. Full
procedures for **all 14 simulation sets** are in
[VIVADO_START_HERE.md](../VIVADO_START_HERE.md). The simulator's result log is
`vivado/riscv_soc_lab/riscv_soc_lab.sim/<set>/behav/xsim/simulate.log`.
If signals were added after the run, use **Restart > Run All**. If you
changed source code, use **Relaunch Simulation** so it recompiles.

## 3. Program the three board tests

These tests use only the PL clock and the eight user LEDs. Leave external
Pmods disconnected for this visit's tests. No UART connection is required.

1. With lab staff, confirm the physical board is the target ZedBoard and
   use its documented power and JTAG-boot setup. Use the board's **USB-JTAG
   connector J17**, not its USB-UART connector. Do not change bank-voltage
   jumpers for these clock/LED tests.
2. In Vivado, select **Open Hardware Manager > Open Target > Auto Connect**.
3. Select the **XC7Z020** and click **Program Device**.
4. Set **Bitstream file** to the first image below. Leave the debug-probes
   `.ltx` field empty. Click **Program**, then observe for at least 10 seconds.
5. Record the filename and LED result. Repeat Program Device for the next
   image; each replaces the previous design temporarily through JTAG.

Use these images in order, relative to the extracted project:

1. `build/zedboard_alu_demo/zedboard_alu_demo.bit`
   — checks the ALU directly using fixed arithmetic/logic test cases.
2. `build/zedboard_cpu_demo/zedboard_cpu_demo.bit`
   — the custom CPU executes a program using ROM/RAM and a test MMIO device.
3. `build/zedboard_aes_demo/zedboard_aes_demo.bit`
   — the CPU loads keys/plaintexts, launches AES, reads and checks four
   encrypted blocks, and stores them in RAM. A separate hardware observer
   also checks all 16 ciphertext words and the four START commands.

For **each** healthy image:

- **LD0 blinks**, roughly one on/off cycle per second: the clock is running.
- **LD1 stays ON**: the application self-test passed.
- **LD2 through LD7 stay OFF**.

LD3 is the running indication and can finish too quickly to see. The
board's separate configuration DONE LED is not the application PASS LED.
For the AES image, LD7:LD4 show a diagnostic code if LD2 lights; see
[the AES board guide](zedboard_aes_demo.md). Save the exact pattern before
trying another image.

Reprogram the AES image **three times** and confirm the same result each
time. Reprogramming gives a fresh startup reset. Do not use the PROG button
as an application reset: it clears the FPGA configuration. These images
are temporary; power loss also removes them. Flash programming is not part
of this procedure.

## If something stops you

- **Device not found:** ask staff to check power, the USB data cable,
  JTAG connector, drivers, and boot setup. Save the Hardware Manager message.
- **Source files missing:** extract the complete folder and open that copy.
- **Simulation runs but never reaches PASS:** confirm Run All, then keep
  the first error and full `simulate.log`.
- **LD0 blinks but LD1 does not light, or LD2 lights:** photograph all
  eight user LEDs and record the exact image used. Do not mark it passed.
- **A different Vivado version must upgrade the project:** work on a copy
  and record the version. Supplied images can be programmed without rebuilding.

You do not need to run synthesis during the lab when using supplied images.
Any rebuilt image needs its own passing routed timing/DRC check before use.
